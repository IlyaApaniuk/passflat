# Legal templates — overview & rollout recommendations

This folder holds **draft, fill-in-the-blank legal document templates** that PassFlat plans to offer as
downloadable files, one per listing type. They are **not wired into the UI yet** — this is a working set we
iterate on, then hand to a Polish lawyer for review.

## Contents

| File                               | Listing type  | Polish doc                       | Status |
| ---------------------------------- | ------------- | -------------------------------- | ------ |
| `00-research.md`                   | —             | Legal research (EN, team-facing) | draft  |
| `cesja-umowy-najmu.md`             | `replacement` | Cesja umowy najmu (3-way)        | draft  |
| `umowa-podnajmu.md`                | `sublet`      | Umowa podnajmu                   | draft  |
| `umowa-wspollokatorska.md`         | `roommate`    | Umowa współlokatorska            | draft  |
| `translations/<doc>-{en,ru,uk}.md` | —             | Informational translations       | draft  |

The Polish `.md` files are the **binding** source of truth. The files in `translations/` are
**informational only** — each carries an "informational translation, the Polish version is binding"
banner plus the Polish disclaimer line, and is shipped as **PDF only**.

## Building the downloadable assets

Run the build script to (re)generate everything in `public/documents/`:

```bash
brew install pandoc typst   # one-time: pandoc + the PDF engine
./scripts/build-templates.sh
```

It produces, per document:

- **Polish:** `<doc>.docx` (editable) + `<doc>.pdf` (read-only)
- **en / ru / uk:** `<doc>-<lang>.pdf` (read-only, informational)

DOCX is generated by pandoc directly from Markdown; PDF is generated by pandoc using **typst** as the
engine (chosen over LaTeX because it is lightweight and renders both Polish diacritics and Cyrillic out
of the box). Re-run the script whenever a `.md` source changes.

> ⚠️ Every template carries a prominent disclaimer that it is a **non-binding draft requiring legal review**.
> Do **not** publish any of them to users before a radca prawny / adwokat sign-off. See `00-research.md` for
> the legal reasoning and the open ⚠️ questions per document.

### Headline legal finding (read before anything else)

**Landlord (Wynajmujący) consent is the make-or-break issue for two of the three documents:**

- **Cesja umowy najmu (`replacement`):** transferring the tenant's _whole_ position needs **przelew
  wierzytelności (art. 509 k.c.) + przejęcie długu (art. 519 k.c.)**. Assumption of debt is valid **only with
  the landlord's consent**, **in writing under pain of nullity (art. 522 k.c.)**. → We ship it as a
  **tripartite (3-way) agreement** signed by outgoing tenant, incoming tenant, and landlord.
- **Podnajem (`sublet`):** **art. 668² (688²) k.c.** — a residential tenant **may not sublet without the
  landlord's consent** (sole exception: a person owed maintenance / obowiązek alimentacyjny). Subletting
  without consent can get the main lease terminated. → Consent is built in as a required attachment.
- **Współlokator (`roommate`):** drafted as an **internal cost-share/coexistence agreement** that does _not_
  itself grant occupancy; if one tenant takes in a roommate, that's effectively podnajem and the consent rule
  applies.

## 1. Recommended distribution FORMAT

**Recommendation: ship each template as a paired `DOCX` (editable) + `PDF` (read-only), generated from the
Markdown source of truth. Treat the `.md` files in this folder as the canonical source.**

Rationale:

- **DOCX** is what ordinary Polish renters actually need — they open it in Word / Google Docs / LibreOffice,
  fill the `[...]` placeholders, and print or e-sign. It's the dominant format for Polish legal-doc downloads
  (every competitor wzór is DOCX/PDF).
- **PDF** is for reading/printing and preserves formatting; good for the "preview before download" case and
  for a clean printable copy.
- **Markdown as source** keeps the content diff-able and reviewable in git, and lets us regenerate both
  outputs deterministically (e.g. `pandoc template.md -o template.docx` / `-o template.pdf`). This avoids
  format drift between the editable and read-only versions.

Why **not** a Google Docs "make a copy" link as the primary channel:

- Pros: zero hosting, instant edit. Cons: requires a Google account, harder to localise/version under our
  control, weaker offline story, and the legal disclaimer is easier to strip. Fine as a _secondary_
  convenience link, but not the system of record.

Suggested per-document output set:

```
cesja-umowy-najmu.md      (source, in repo)
└── cesja-umowy-najmu.docx (editable, distributed)
└── cesja-umowy-najmu.pdf  (read-only, distributed)
```

Build step (proposal, not yet implemented): a small script using `pandoc` (or `docx`/`md-to-pdf` in Node)
that converts each `.md` to `.docx` + `.pdf` and writes them to the storage location chosen below.

## 2. Localisation (en / ru / uk)?

**Recommendation: keep Polish as the only _binding_ version; produce en/ru/uk as clearly-marked
_informational_ translations — and only after the Polish drafts are lawyer-approved.**

- These are documents governed by **Polish law** and intended to be signed in Polish. Translations carry real
  risk if treated as operative.
- PassFlat serves a large non-Polish-speaking audience (en/ru/uk locales exist), and a foreigner renting in
  Warsaw is exactly who benefits from understanding a cesja/podnajem. So translations have clear product value
  — as comprehension aids, not as the signed instrument.
- Each translation must carry a banner, e.g.:
  > _"Tłumaczenie informacyjne. Wersją wiążącą jest wersja polska. / Informational translation. The Polish
  > version is the binding one."_
- Sequencing: **PL drafts → lawyer review → PL final → then translate**. Translating drafts wastes effort and
  risks shipping inconsistent legal content. Suggested layout once we get there:

```
docs/legal-templates/
  pl/  cesja-umowy-najmu.md          (binding)
  en/  cesja-umowy-najmu.en.md       (informational)
  ru/  cesja-umowy-najmu.ru.md       (informational)
  uk/  cesja-umowy-najmu.uk.md       (informational)
```

(For now everything lives flat in this folder in Polish; restructure into `pl/` etc. when we add translations.)

## 3. Storage / file layout (given the existing Supabase setup)

Today the app uses a **public Supabase Storage bucket `listing-photos`**, accessed server-side with the
service-role key (see `src/lib/supabase/storage-server.ts`). Two viable options for the templates:

### Option A — `public/documents/` static folder in the Next.js app ✅ recommended (for now)

Put the generated DOCX/PDF under `public/documents/legal-templates/` and serve them as static assets
(`/documents/legal-templates/cesja-umowy-najmu.docx`).

- **Pros:** zero infra; versioned in git alongside the source `.md`; instant CDN caching via the hosting
  platform; trivial to link from the UI; easy rollback; no bucket/RLS config. Perfect fit because these are a
  **small, fixed set of public, rarely-changing files**.
- **Cons:** every change ships with a deploy (fine — these change infrequently and _should_ go through review
  anyway); not suitable if we later need per-user generated/pre-filled copies.

### Option B — separate public Supabase bucket `documents` (or `templates`)

Mirror the `listing-photos` pattern with a new public bucket.

- **Pros:** consistent with existing storage approach; lets us update files without a redeploy; natural home
  if we later generate **personalised, pre-filled** documents per listing/user (server fills placeholders →
  uploads → returns a signed/public URL).
- **Cons:** more moving parts (bucket creation, RLS/policies, upload pipeline) for what is currently just a
  handful of static public files; content no longer co-located with source in git.

**Recommendation:** start with **Option A** for the static blank templates (simplest, versioned, public,
fixed set). **Plan to move to Option B** _only_ when/if we add the dynamic, pre-filled-per-listing feature —
at which point a dedicated `documents` bucket (separate from `listing-photos`, with its own access policy) is
the right call. Keep the `.md` files in `docs/legal-templates/` as the source of truth in both cases.

## Feature flag — enabling / disabling the whole feature

The downloadable-templates feature is gated behind a single build-time env flag so it can be turned
on or off cleanly without code changes:

| Var                                      | Values             | Default |
| ---------------------------------------- | ------------------ | ------- |
| `NEXT_PUBLIC_FEATURE_DOCUMENT_TEMPLATES` | `"true"`/`"false"` | ENABLED |

- It is a `NEXT_PUBLIC_*` var so the same value is available in **server and client** components
  (no hydration mismatch).
- **Default is ENABLED**: the feature is on unless the var is explicitly set to the string `"false"`.
  An unset or empty var keeps it enabled.
- The single source of truth is `isDocumentTemplatesEnabled()` in `src/lib/feature-flags.ts`.

When set to `"false"`, the feature leaves **no visible trace**:

1. The `TemplateDownload` component renders `null` (and each call site is additionally guarded so no
   surrounding labels/wrappers render) — covers the resources grid, listing detail
   (replacement/sublet/roommate), how-it-works signing step, and the cesja blog CTA.
2. The contextual chat hint in `chat-window.tsx` does not render.
3. The `/resources` route returns a **404** via `notFound()`, and the `/resources` links are removed
   from the footer (`src/components/landing/footer.tsx`) and the sitemap (`src/app/sitemap.ts`).

> Note: the cesja blog CTA is rendered by a React component (`BlogArticle`), not inside the static
> MDX, so it is gated together with the other call sites. The MDX content itself contains no download
> CTA, so nothing in the `.mdx` files needs the flag.
