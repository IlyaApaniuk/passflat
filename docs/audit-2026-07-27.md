## 1. Безопасность

### 🔴 C1. RLS выключен на `pois` и `building_tags` — публичное чтение, запись и удаление

**Файлы:** `prisma/migrations/20260727100806_add_osm_pois/migration.sql`, `prisma/migrations/20260727135319_add_building_tags/migration.sql`

✅ verified: в репозитории **ноль** стейтментов `ENABLE ROW LEVEL SECURITY` / `CREATE POLICY` (grep по `prisma/migrations` и `supabase/` пуст). RLS для старых таблиц включали руками в дашборде, а две таблицы от 27.07 пропустили. Живые пробы (безопасные: чтения + инсерты `{}`, падающие на `id NOT NULL`, + UPDATE/DELETE по несуществующему id):

| проба                                                                      | результат                                                 |
| -------------------------------------------------------------------------- | --------------------------------------------------------- |
| `GET /rest/v1/pois?select=*` (anon)                                        | 206, `content-range: 0-999/47286` → **читается целиком**  |
| `POST /rest/v1/building_tags {}`                                           | `23502 null value in column "id"` → **инсерт прошёл RLS** |
| `DELETE /rest/v1/pois?id=eq.<none>`                                        | 204 → **право на удаление есть**                          |
| `PATCH /rest/v1/pois?id=eq.<none>`                                         | 204 → **право на апдейт есть**                            |
| остальные 23 таблицы (`profiles`, `cost_reports`, `messages`, `payments`…) | `42501 violates RLS` → защищены                           |

**Сценарий:** anon-ключ публичен (лежит в JS-бандле).
`curl -X DELETE 'https://auth.passflat.com/rest/v1/pois?id=not.is.null' -H 'apikey: <anon>'` стирает все 47 286 POI → чекер адресов и location-score мертвы, пока не прогонишь `prisma/import-osm-pois.ts`. По `building_tags`: массовая накрутка голосов с подделанным `voter_key`, подделка `source='cost_report'` (та самая пометка «от жильца», по которой UI сортирует), выставление `is_visible`, удаление всех тегов — мимо ханипота, IP-лимитера и серверной логики провенанса.

**Фикс** (миграцией в git, не руками в дашборде):

```sql
ALTER TABLE public.pois          ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.building_tags ENABLE ROW LEVEL SECURITY;
-- опционально, приложение не читает их через PostgREST:
REVOKE ALL ON public.pois, public.building_tags FROM anon, authenticated;
```

**Чтобы не повторилось:** `auto_expose_new_tables = false` в `supabase/config.toml:24` и/или CI-проверка «каждый `CREATE TABLE` в новой миграции сопровождается `ENABLE ROW LEVEL SECURITY`». Сейчас каждая новая таблица от Prisma рождается с этой дырой.

### 🟠 H2. Приватные чаты вещаются в публичные Realtime-каналы

**Файлы:** `src/lib/supabase/broadcast.ts:17-41` ✅ verified, `src/hooks/use-chat.ts:73-74`, `src/app/[locale]/messages/client.tsx:44-45`, `src/hooks/use-unread-count.ts:35`, `src/hooks/use-presence.ts:13-14`

Каналы создаются без `{ config: { private: true } }`, Realtime Authorization не включён. Живая проба: неаутентифицированный клиент с публичным anon-ключом подписался на `chat:notifications:<произвольный-uuid>` и получил `SUBSCRIBED`. Пейлоад содержит **текст сообщения**: `{ id, content, senderId, senderName, createdAt, conversationId }`.

**Сценарий:** `authorId` публичны — `GET /api/listings` отдаёт полные строки Prisma (`src/app/api/listings/route.ts:447-460`). Атакующий собирает все `authorId`, подписывается на `chat:notifications:<id>` и пассивно читает всю переписку с именами отправителей, затем подписывается на `chat:<conversationId>` в обе стороны. Канал `online-users` вдобавок позволяет перечислять, кто онлайн, и вбрасывать фейковое присутствие.

**Фикс:** `{ config: { private: true } }` на всех `supabase.channel(...)` + включить Realtime Authorization + политики на `realtime.messages` (свой id в суффиксе канала / участник `conversation_participants`). Серверные бродкасты и так идут через service-role. Минимальная затычка: убрать `content`/`senderName` из пейлоада и слать пустой пинг «обнови» — клиенты и так дозапрашивают через аутентифицированный `/api/conversations`.

### 🟠 H3. Статус объявления не фильтруется на детальной странице

**Файлы:** `src/lib/listing-detail-query.ts:13-24` ✅ verified (в `listingWhere` только slug/id), `src/app/[locale]/[city]/replacement|sublet|roommate/[id]/page.tsx`, `src/app/api/listings/[id]/route.ts:47-70`

Списочные эндпоинты фильтруют `status: 'active'` правильно — дыра только на прямых URL, а именно ими и делятся.

- Админ закрывает жалобу с `hideListing: true` → `status='removed'`, объявление уходит из поиска, **но каноничный URL продолжает отдавать его целиком с телефоном/телеграмом скамера**. DSA-процедура фактически не исполняется.
- Удаление аккаунта ставит `status='deleted'` (`src/app/api/account/route.ts:52-55`), но объявление с контактами остаётся публичным все 30 дней soft-delete — дыра в GDPR-стирании.
- Превышение лимита из 2 бесплатных даёт `status='pending_payment'` — человек просто шарит прямую ссылку и не платит.

**Фикс:** `status: 'active'` в `listingWhere` (владельцу и админу — отдельная ветка), то же в `GET /api/listings/[id]`.

### 🟡 Medium

- **M4. Гейт удалённого аккаунта fail-open + не проверяется ни в одном API.** `src/middleware.ts:100-134` читает `deleted_at` через Supabase-клиент (единственный PostgREST-запрос в приложении) — зависит от RLS-политики, которой в репозитории нет. - **M5. Лимитер анонимных отчётов обходится, а его глобальный предохранитель — self-DoS.** `src/app/api/cost-reports/route.ts:30-37, 75-103`. Скрипт (а) травит медианы правдоподобными значениями, не поднимая ни одного алерта, (б) выбрав 200/час, отдаёт **всем живым посетителям `429`** — то есть копеечный скрипт глушит основную воронку. Безлимитные публичные запросы.** `GET /api/listings?limit=1000000` уходит прямо в `take`; `?page=-5` → отрицательный `skip` → 500. `GET /api/cost-reports` тянет все здания города со всеми отчётами без `take` и пагинации. `getBuildingsData` кеширован по пользовательскому `?q=` → безлимитное число ключей кеша, каждый за тем же джоином. Фикс: `Math.min(Math.max(1, limit), 100)`, `page >= 1`, пагинация, нормализация `q` (≤64, trim, lowercase).
- **M7. Неаутентифицированная email-амплификация + тихое создание аккаунтов.** `src/app/[locale]/auth/actions.ts:135-206, 220-262, 48-101` — три POST-абельных server actions без рейт-лимита, обходят троттлинг Supabase (шлют через `admin.generateLink()` + Resend). Скрипт по собранным адресам жжёт квоту Resend и метит домен как спам (заодно ломая транзакционную почту — чеки, уведомления). Хуже: строки 158-165 на **любую** ошибку `generateLink` вызывают `createUser({ email_confirm: true })` → массовое создание подтверждённых аккаунтов на чужие адреса + сквоттинг адреса до того, как придёт настоящий владелец. Фикс: рейт-лимит по IP и по целевому email, `createUser` только на ошибку «user not found», Turnstile на форме.
- **M8. `/api/listings/[id]/translate` — бесплатный слив квоты DeepL.** Без авторизации, лимита и проверки владельца; id публичны. Стоимость ограничена `объявления × 3`, но триггерится мгновенно и заново для каждого нового.
- **M9. Весь рейт-лимитинг — в памяти инстанса, две мапы растут без границ.** `contact/route.ts:5-21`, `city-notify/route.ts:9-25` не эвиктят записи (в `building-tags` и `location-checker` — сделано правильно). На Vercel лимит по факту = `N инстансов × лимит`, холодный старт обнуляет. «3 в минуту» на контакт-форме превращается в неограниченный релей в твой инбокс, причём `replyTo` контролируется атакующим.

## 2. Надёжность и целостность данных

### 🟠 A1. Правка отчёта с сезонной коммуналкой сохраняет старое среднее — портит `totalMonthlyAvg`

**Файлы:** `submit/page.tsx:111-119`, `submit/client.tsx:560-591`, `api/cost-reports/[id]/route.ts:131-156`

Префилл кладёт сохранённое среднее в одиночное поле (`electricity: String(report.electricityAvg)`) и автоматически открывает сезонный вид зима/лето. В сезонном виде одиночный инпут не рендерится — но `utilityFields` его всё равно отправляет, а сервер предпочитает одиночное значение сезонному. Итог: жилец правит зиму 300→500, видит «успешно», а `electricityAvg`/`heating` и пересчитанный `totalMonthlyAvg` остаются **старыми** — незаметно, из UI не чинится, и это уходит в медианы. Именно этот флоу гонит крон «обнови свой годовалый отчёт». Новые отчёты не затронуты (тумблер очищает поле).
**Фикс:** `electricity: showElectricitySeasonal ? undefined : …` (то же для heating) и/или на сервере предпочитать зиму/лето, когда обе заполнены.

### 🟠 A2. Новый отчёт не виден на странице здания до часа — ревалидации нет нигде

**Файлы:** `building/[slug]/page.tsx:24` (`revalidate = 3600`), `api/cost-reports/route.ts` (POST без ревалидации), `src/lib/cost-aggregates.ts:118` (`tags: ['costs']`)

✅ verified: кеши помечены тегом `['costs']`, но `revalidateTag`/`revalidatePath` не вызываются **нигде в кодовой базе** (grep пуст). После отправки экран успеха ведёт на страницу здания — ISR до часа — где отчёта нет. Петля анонимного клейма («войди, чтобы разблокировать») ведёт туда же; хаб города и районы (`revalidate = 3600`) так же протухшие; письма подписчикам «N новых отчётов» линкуют на ту же страницу. «Я отправил, а его нет» бьёт ровно в петлю «внёс → увидел себя», ради которой всё построено.
**Фикс:** в успешных путях POST/PATCH звать `revalidateTag('costs')` + `revalidatePath` для `/[locale]/[city]/building/[slug]` (все локали), часовой флор оставить для краулеров.

## 3. SEO и локали

- **🟡 B1. ### Найдено вживую (репорт основателя 28.07) — в тот же CRO-батч

**13. После сохранения отзыва выбор другого адреса не сбрасывает форму.** ✅ verified: `review/client.tsx:202-209` монтирует `<BuildingTagPicker>` **без `key`**, а компонент держит `selected` и `status` в локальном состоянии (`building-tag-picker.tsx:51-52`) и при `status === 'saved'` делает ранний return с карточкой «спасибо» (`:87-115`). Меняется `building.id` — React переиспользует тот же инстанс, состояние живёт. Итог: человек отметил дом, выбрал другой адрес и видит «сохранено» для **предыдущего** дома, оценить новый нельзя вообще. Это обрывает ровно тот сценарий, который мы хотим растить (отметил свой дом → отметил дом, который смотришь). Фикс — одна строка: `key={building.id}` на пикере (там же имеет смысл добавить и на монтировании в `submit/client.tsx:873` для единообразия).

**14. Взаимоисключающие теги выбираются одновременно.** ✅ verified: `toggle` (`building-tag-picker.tsx:54-59`) просто добавляет/убирает ключ, никаких групп; словарь (`src/lib/building-tags.ts:27-75`) содержит прямые противоположности. Можно отметить «легко парковаться» **и** «сложно с парковкой». Хуже: положительные теги публикуются **с первого голоса** (`aggregateTagVotes`, `:131-161`), так что один человек — случайно или намеренно — выводит на карточку дома «тихий дом» рядом со «слышно соседей». Это бьёт по пиллару репутации, где вся ценность — доверие к чипам.

Пары/группы, которые реально противоречат друг другу:

| группа      | ключи                                                                                          |
| ----------- | ---------------------------------------------------------------------------------------------- |
| парковка    | `easyParking` ↔ `hardParking`                                                                  |
| зима        | `warmInWinter` ↔ `coldInWinter`                                                                |
| управляющий | `repairsHandledFast` ↔ `repairsIgnored`                                                        |
| подъезд     | `tidyEntrance` ↔ `neglectedEntrance`                                                           |
| лифт        | `workingElevator` ↔ `elevatorBreaks` ↔ `noElevator` (трёхсторонняя: «лифта нет» исключает оба) |
| тишина      | `quietBuilding` ↔ `neighborsAudible` / `streetAudible` / `thinFloors`                          |

Последняя группа — единственная спорная: дом может быть тихим по соседям, но шумным по улице. Но «тихий дом» — это обобщающее утверждение, и любая конкретная жалоба на шум его опровергает, так что взаимоисключение оправдано.

**Как чинить (рекомендация):** добавить в `BuildingTagConfig` поле `exclusiveGroup?: string`, в `toggle` при выборе снимать остальные ключи той же группы (поведение как у радиокнопки внутри группы, но с возможностью снять выбор совсем), и продублировать проверку в `POST /api/building-tags` — payload с двумя ключами одной группы отклонять 400 (клиент этого не допустит, но защищает от скриптов и устаревших вкладок). Альтернатива «одно свойство — три состояния (хорошо/нейтрально/плохо)» честнее моделирует реальность, но это переделка UI и хранения — не в режиме заморозки фич.

### Измерения

- **⚠️ PostHog отключён до согласия на куки** (`posthog-provider.tsx:105`: `opt_out_capturing_by_default: consent !== 'accepted'`). Все клиентские события ($pageview, `cost_form_started`) теряются для тех, кто проигнорировал баннер — на мобильном соцтрафике это большинство. При этом серверный `cost_report_submitted` **не** гейтится. Значит числитель и знаменатель твоей воронки считаются по разным популяциям: «view→click <1%» и «15,8%» посчитаны по согласившемуся подмножеству. Бесплатный первый шаг: сравнить визиты Vercel Analytics (cookieless, всегда включён) с $pageviews PostHog — измерить размер слепого пятна.
- **Не хватает событий:** `cost_form_abandoned` с состоянием заполнения по секциям (главный пробел — сейчас между стартом и попыткой отправки не видно, где отваливаются), `cost_form_draft_restored/discarded`, единое `cta_click{placement}` (кнопки в шапке, карточки районов, CostTransparency сейчас не логируют ничего), `consent_banner_shown/accepted/declined`, `share_completed`.
- **Есть и работает:** ~40 событий, включая `cost_form_started{city,source}`, `address_checked`, `checker_cta_clicked`, `auth_started`, UTM и `?ref` как super-properties; серверные `cost_report_submitted`, `referred_signup` — независимы от согласия.

## 6. Проверено и в порядке

**Безопасность:** Stripe-вебхук (проверка подписи, идемпотентность, откат доступа при возврате) · защита от подмены цены (серверный `STRIPE_PRICES`, никаких клиентских сумм) · админ-авторизация (`getAdminUser()` — серверный allowlist, применён и на страницах, и в API, не только на клиенте) · отсутствие mass assignment (все роуты собирают `data` по полям) · IDOR (все `[id]`-роуты скоупятся по `user.id`, чаты — по членству) · ноль `$queryRaw`/`$executeRaw` во всём репозитории · XSS (3 места `dangerouslySetInnerHTML`, все недостижимы для пользовательского ввода; письма — React Email) · `safeNextPath` (многослойное декодирование, нормализация точечных сегментов) · unsubscribe-токены на HMAC-SHA256 + `timingSafeEqual` · секретов в git нет (`.env*` никогда не коммитились, CI на `pull_request`, service-role только в 4 серверных модулях) · SSRF нет (единственный внешний fetch — DeepL по фиксированному URL) · браузерный Supabase используется только для сессии и Realtime, ни одного клиентского `.from('table')`.

**Данные:** математика медиан (пустые множества, N=1, деление на ноль, MAD-трим — везде защищено) · nullable Decimal обёрнуты `num()`/`Number.isFinite` · энумы совпадают с UI · логика `utilitiesComplete` когерентна · PR #90 (Set-Cookie/ISR) чистый · `/api/location-score` образцовый (ретрай P2002, дедуп in-flight, кулдаун, предохранитель) · sitemap/robots корректны · автосохранение черновика работает как задумано · польская запятая в числах не портит данные (браузер блокирует отправку нативно).

**Производительность:** mapbox везде ленивый, `optimizePackageImports`, next/image, N+1 в горячих путях нет, LCP героя — серверный HTML без картинки.
