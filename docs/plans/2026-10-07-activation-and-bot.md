**Passflat: план реализации — понятные сценарии, достоверные данные и Telegram**

Дата: 7 октября 2026. Статус: ТЗ для реализации другим агентом; код по этому плану ещё не изменён.

**1. Задача и факты**

Подготовить существующий продукт к измеримому эксперименту: понять, получают ли пользу люди, которые ищут комнату/соседа или проверяют конкретный адрес, и устранить разрывы между сайтом и ботом.

Данные от основателя: 320 отчётов, 318 зданий, 20–30 самостоятельных вкладов, оплат нет. Собственные тестовые посещения уже исключены. В показанных строках Google Search Console 10 из 13 кликов относятся к поиску соседа. Это НЕ доля всего трафика. Периоды скриншотов и соответствие запросов страницам не подтверждены.

Эта итерация не выбирает новый бизнес окончательно. Поиск соседей остаётся существующей точкой входа; проверка адреса — самостоятельной полезной задачей; бот — каналом этих задач и уже существующего сценария залога.

**2. Границы работы**

- Реализовать пакеты A–E ниже последовательно, небольшими обозримыми изменениями.
- Переиспользовать существующие формы, маршруты, события, локализацию и компоненты.
- Сохранить URL страниц домов и поиска соседей, canonical и hreflang. Не менять URL ради этой итерации.
- Сайт: поддержать PL/EN/RU/UK. Бот: сохранить существующие RU/UK; дополнительные языки отложить.
- Не строить подбор совместимых соседей, отдельные профили ищущих людей, новый чат, CRM, рейтинг агентств, оплату или новый город.
- Не добавлять уведомления о новых объявлениях/отчётах в эту итерацию. Убрать обещания доставки, которой ещё нет. Существующие напоминания по кейсу залога сохранить.
- Не делать глобальный редизайн, не менять модель согласия на аналитику и уже настроенное исключение тестов.
- Новые таблицы БД для этой итерации не требуются. Сначала проверить возможности текущей схемы; production-миграции и отправки пользователям не выполнять как часть локальной реализации.
- Старые ограничения в исторических DEVELOPMENT_PLAN.md и docs/plans описывают прежний этап. В рамках текущего ТЗ разрешены перечисленные исправления roommate и бота; это не разрешение развивать весь маркетплейс.

**3. Перед изменениями**

- Прочитать актуальные инструкции репозитория, проверить рабочее дерево. Не перезаписывать чужие изменения.
- Зафиксировать, какие перечисленные возможности уже существуют. Не создавать второй waitlist или второй переход на проверку адреса.
- Различать состояние кода и состояние production. README бота упоминает неприменённые миграции, но сам по себе не доказывает текущий статус развёртывания.
- Подготовить локальные/mock-данные для состояний: нет предложений; предложения есть, фильтр исключает все; одно наблюдение по дому; только объявления; смешанные источники; неполные расходы; нет данных дома, есть район; нет данных района, есть город; нет числовых данных вообще.

Проверить `search_performed.results_count`: сейчас код использует исходный массив объявлений. Число должно соответствовать результатам действующих фильтров; изменение области карты не должно выглядеть как новый поисковый запрос без действия пользователя.

Приёмка A: один переход/одно действие создаёт ожидаемое число событий; повторный рендер не дублирует события. Цепочка roommate → checker → форма сохраняет доступный контекст. Ошибка API не создаёт событие успеха. Отсутствие SDK не ломает сценарий. Не обещать восстановление прошлой атрибуции или сопоставление Google-запроса конкретному посетителю.

Основные файлы:

Первый экран roommate должен ясно разделять две уже поддерживаемые роли:

- «Ищу комнату» / `Szukam pokoju`: переход к существующим объявлениям и фильтрам; при отсутствии предложений — существующий сбор интереса.
- «Есть свободная комната» / `Mam wolny pokój`: существующий `/create-listing?type=roommate`, с сохранением выбора через авторизацию.

Третий сценарий «ищу человека для совместного поиска квартиры» пока не добавлять: модели профиля такого человека и процесса обработки заявки нет. Не маскировать этот сценарий обычным объявлением с обязательным адресом.

Существующий переход на проверку адреса сохранить как вторичную помощь: «Нашёл вариант? Проверь адрес и известные расходы». Не требовать заполнения расходов для просмотра предложений или перехода в checker.

Исправить три класса подписок без изменения уникального ключа БД:

| Назначение                         | `listingType` | `districtSlug` |
| ---------------------------------- | ------------- | -------------- |
| Ожидание запуска города            | пусто         | пусто          |
| Интерес к объявлениям всего города | задан         | пусто          |
| Интерес к объявлениям района       | задан         | задан          |

Сейчас API сохраняет `listingType` только внутри ветки непустого района. Исправить независимую валидацию типа и района: запрос roommate без района должен сохранять `listingType=roommate`. Для объявлений валидировать реальный город и принадлежность района городу. Для прежней формы запроса нового города сохранить её текущую семантику.

Рассылку `city-launch` ограничить настоящими подписками запуска города: `listingType=''`, `districtSlug=''`, действующее согласие и остальные существующие условия. Заявки объявлений не должны получать confirmation/launch email про запуск города. Старые записи с потерянным типом автоматически не переименовывать: исходное намерение неизвестно.

Копирайт сбора интереса должен честно описывать результат: «Сохранить интерес»; подтверждение сообщает, что интерес сохранён и автоматических уведомлений о новых предложениях пока нет. Не обещать подбор или обязательный ответ основателя. Существующее согласие сохранить.

Отличать отсутствие предложений во всём городе от нуля после фильтра. При жёстких URL-фильтрах и перезагрузке не показывать «в городе пока нет объявлений», если предложения есть вне фильтра. При необходимости передать отдельный серверный признак наличия предложений вне пользовательских фильтров. Ноль после фильтра → предложить изменить фильтры.

Приёмка B: все три вида подписок разделены; повторная отправка не создаёт дубль; неверные тип/район отклоняются; неизвестный район не превращается в запрос запуска города. Проверка письма через mock подтверждает отсутствие неподходящих отправок. Два пути roommate работают на мобильном; сценарии replacement/sublet сохраняют прежнее поведение. Новых реальных писем в ходе тестов не отправлять.

**6. Пакет C — достоверный ответ по дому на сайте и в общей логике**

Основные файлы:

- `src/lib/cost-aggregates.ts`, `src/lib/cost-baselines.ts`, `src/lib/cost-stats.ts`
- `src/lib/location-checker.ts`
- `src/app/[locale]/[city]/building/[slug]/{page,client}.tsx`
- `src/app/[locale]/[city]/check/client.tsx`
- `src/app/api/cost-reports/route.ts`
- `src/app/[locale]/[city]/costs/submit/client.tsx`
- `src/app/[locale]/page.tsx` и существующие компоненты, которые используют изменённые показатели

Сначала определить единый небольшой контракт данных, переиспользуемый сайтом и ботом: источник и его количество, количество пригодных наблюдений для конкретной метрики, полнота расходов, доступная дата и её значение, географический уровень. Не создавать второй независимый алгоритм для Telegram.

Правила отображения:

- Раздельно показывать сведения `user`, `import`, `scraped`. `user` означает сообщение пользователя, а не проверку документом. `import` без дополнительных доказательств обозначать как внесённые данные; не присваивать ему верификацию автоматически.
- Не объединять объявления и сообщения жильцов в одну цифру под подписью «реально платят». Для смешанной базы показывать отдельные группы и их размеры; выбранная группа должна явно подписываться на карте, карточках и в baseline.
- Один отчёт: «Одно наблюдение по этому адресу», с характеристиками жилья, если они известны. Не выдавать его за установленную цену дома.
- `utilitiesComplete=false` означает, что полная стоимость не установлена, независимо от источника. Такой итог показывать как известную часть расходов и исключать из группы полных all-in сумм. Не терять исходные записи.
- Нулевые подтверждённые расходы и неизвестные расходы различать. Не превращать `null` или отсутствие счётчиков в ноль.
- Для каждого числа считать N пригодных значений, не общее число всех записей здания.
- Дату добавления/подтверждения записи не выдавать за период фактического платежа. Если период неизвестен, сказать это явно.
- Убрать вывод «переплачиваешь/экономишь» из простого сравнения с районной медианой. Нейтральное сравнение допустимо только с объяснением состава выборки; при несопоставимых типах жилья сравнительный вывод скрыть.
- Фильтр «комната/квартира» должен ограничивать исходные отчёты до агрегации. Сейчас преобладающий тип здания выбирается отдельно от общей медианы — это позволяет смешать цены комнат и квартир.
- N≥5 не называть доказательством проверенности или репрезентативности. Статистическую модель справедливой цены в этой итерации не строить.

Первый экран дома: адрес → какие сведения есть и откуда → известные расходы с ограничениями → два понятных действия: посмотреть подробности / добавить свой опыт. Существующие location score, теги, отзывы, форма и префилл адреса переиспользовать. Раскрытие источников и ограничений не прятать за contribution-gate.

Fallback: отдельно сообщать «по дому данных нет», затем явно подписанный ориентир по району/городу. Если числовых данных нет и на этом уровне, показывать это состояние и доступные сведения об окружении; не генерировать обязательную цифру. Районные сведения не обозначать сведениями дома.

При изменении общих helpers проверить всех потребителей и cache tags, чтобы hero, карта, страница дома, checker и бот не показывали разные значения одного и того же показателя. Не менять тарифы калькулятора предположениями; обнаруженные устаревшие источники оформить отдельным проверяемым пунктом.

Приёмка C: фикстуры для user/import/scraped/mixed, одной записи, неизвестной коммуналки, нулевых значений, смешанных комнат/квартир и отсутствия пригодных наблюдений. Совпадение показателей сайта и бота при одинаковой выборке. Ни один из этих случаев не превращается в неподтверждённое «проверено» или «переплата».

**7. Пакет D — Telegram: исправить переход и обещания**

Основные файлы:

- `src/components/costs/telegram-bot-cta.tsx`
- `src/lib/bot/{bot,lookup,format,texts,store,analytics}.ts`
- `src/lib/bot/{deposit-flow,deposit-texts,contract,deposit}.ts`
- `src/lib/bot/README.md`
- `src/app/api/telegram/webhook/route.ts`
- `src/app/api/cron/telegram-followups/route.ts`

**D1. Исправить website → bot handoff.**

Сайт уже формирует `?start=b_<buildingId>`, но `/start` обрабатывает `dep` и `d_`, а `b_` игнорирует. Добавить обработку существующего формата: проверить UUID, получить публичные данные здания, сразу показать результат по этому адресу. Не просить повторно вводить известный адрес. Для удалённого/неизвестного/неподдерживаемого здания дать понятный fallback и предложить ввод адреса. Не создавать запись здания из произвольного payload.

Переход по ссылке сам по себе не должен подписывать на рассылку. Существующий `d_` также проверить: сейчас он автоматически сохраняет подписку. Показывать район и отдельное явное действие сохранения интереса. Сохранить работоспособность уже опубликованных `dep`, `d_`, `b_`, `web_*` ссылок.

**D2. Использовать честные данные из пакета C.**

Карточки дома, района и соседних зданий должны показывать происхождение цифр и размер выборки. Сейчас `LocationCheckerCosts` знает `sourceKind`, но форматирование бота в основном пишет общее «на основе отчётов». Убрать безусловный ценовой вердикт относительно района для несопоставимых объектов. Различать «одно наблюдение» и «данные нескольких объектов».

Статистику возврата залога формулировать как результаты конкретных ответов с N и географией, без обещания индивидуальной вероятности возврата. Данные проблемных `DepositCase` не добавлять в общую статистику всех арендаторов.

**D3. Исправить обещания уведомлений.**

`TelegramSubscription` хранится, но отправщик новых cost-report уведомлений по нему в репозитории не реализован; cron `telegram-followups` обслуживает другие напоминания — по залогу. Поэтому заменить «Напишу, когда появятся новые данные» на понятное сохранение интереса с явным сообщением об отсутствии автоматических уведомлений. Существующие сохранения и удаление интереса продолжить поддерживать. Не создавать ещё один notifier в рамках этой итерации.

В `/help`, приветствии, кнопках и подтверждениях описывать одинаковый фактический набор возможностей. Не обещать через Telegram поиск соседа, если его нет. Бот предлагает проверку адреса и существующий помощник по залогу.

**D4. Разделить аналитику задач бота.**

Сохранить `tg_bot_started`, `tg_address_checked`, `tg_district_checked` и `tg_deposit_*`. Дополнить события проверки `entry_source`, `lookup_level`, `source_kind`, N и признаком неполных данных, где применимо. При прямом открытии здания учесть этот успешный результат один раз, без двойного счёта с проверкой введённого адреса.

Web-CTA измеряет нажатие ссылки; `tg_bot_started` измеряет фактический старт. Не представлять их как одну идентифицированную межканальную воронку. Сохранить UTM bot → website и префилл адреса в форме, проверить их тестами. Не передавать chat ID в URL сайта.

**D5. Сохранить узкий scope помощника по залогу.**

Не называть текущую функцию полной проверкой договора: она извлекает ограниченный набор условий. Непрочитанный документ, нераспознанный тип договора и неподдерживаемый случай не должны сопровождаться уверенным персональным юридическим выводом.

Не расширять и не переписывать юридические правила по догадке. Подготовить перечень сценариев и ограничений для проверки польским юристом; спорные случаи направлять к квалифицированной помощи без утверждения, что юрист уже назначен.

Кнопка `wants_lawyer` сейчас только фиксирует интерес к ещё не запущенному партнёрству. Объяснить это до нажатия и в подтверждении; не обещать срок ответа, консультацию или гарантированное будущее сообщение. Сохранить событие интереса отдельно от результата юридической помощи.

Для существующих напоминаний по залогу проверить явное согласие, отмену и отсутствие повторной отправки одного напоминания после повторного запуска обработчика. Новых рассылок и исходящих обращений при реализации не выполнять.

Приёмка D: `/start b_<valid>` сразу показывает нужный адрес; invalid/missing/outside-city безопасно обрабатываются; сохранённые ссылки `dep`/`d_` не ломаются; подписка не создаётся от одного открытия; sparse/mixed/incomplete данные подписаны правильно; N и fallback совпадают с сайтом; отказ чтения договора не выдаётся за успешную проверку; обращения к юристу не обещают действующую услугу; RU/UK и HTML escaping работают.

**8. Пакет E — документация измерения и проверка готовности**

Добавить `docs/analytics/activation-funnels.md` с фактическими событиями после реализации, обязательными свойствами и инструкцией настройки отчётов:

1. Roommate: вход → выбор роли → просмотр предложения → контакт; сохранение интереса считать отдельной веткой.
2. Адрес: вход в checker/дом → успешный ответ → действие. Начавший проверку и пришедший прямо на страницу дома — разные входы.
3. Вклад: источник входа → старт формы → адрес → попытка → успех.
4. Telegram address: старт → успешный ответ → сохранение интереса; переходы на сайт анализировать по UTM отдельно.
5. Telegram deposit: старт кейса → результат разбора → письмо → отметка пользователя об отправке → сообщённый исход. Письмо не считать возвратом денег.

Для web-воронок указать окно текущей сессии; для deposit — отдельно описать более длинное окно наблюдения. Не смешивать интервалы, новые и старые события, пользователей и события. Количество сохранённых заявок проверять по БД отдельно от числа клиентских событий. Клик по внешнему контакту не означает ответ или успешное заселение.

Описать, как сравнить две последовательные полные недели после релиза: количество входов по типу страницы, полезные действия, заявки, источники и ошибки. Не включать A/B-тесты, прогноз выручки или универсальные целевые проценты: выборка слишком мала.

Обновить README бота: выполненные функции, сохранённый интерес, работающие напоминания, форматы deep links, проверенный или неизвестный статус production-зависимостей. Не объявлять бот запущенным только по наличию кода/переменной username.
